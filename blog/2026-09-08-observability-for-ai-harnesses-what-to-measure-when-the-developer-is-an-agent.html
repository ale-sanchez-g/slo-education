    Observability for AI Harnesses: What to Measure When the Developer Is an Agent

    AI coding harnesses are production infrastructure now. Learn which signals to collect from agent sessions, stages and tool calls, and how AI-DLC's audit trail becomes telemetry.

    The Build Pipeline Grew a Mind of Its Own

    For twenty years the software factory was boring in the best possible way. A commit landed, a runner picked it up, a fixed sequence of steps ran, and the result was pass or fail. When something broke you read the log, and the log told you exactly which step failed because the steps never changed.

    An AI harness is not that. It is a long-running, stateful, non-deterministic process that reads your repository, holds a conversation, dispatches sub-agents, writes files, runs commands and occasionally asks a human for permission. It makes decisions. It has a working memory that fills up. It can be slow for reasons no stack trace will explain. It is, in every way that matters to an SRE, a distributed system that has quietly been promoted into the critical path of your delivery.

    And most teams are running it with no telemetry at all.

    What "Observability" Means Here

    The question observability answers is the same one it always answered: can you ask a new question about the system's behaviour without shipping new code to find out? For an agent harness, the new questions arrive weekly. Why did last Tuesday's runs all stall at the same stage? Which repository consistently produces the most rework? Did the model change on the seventeenth, and did anything get worse? Are we paying more per merged change than we were a month ago?

    None of those are answerable from a terminal transcript. They need an event stream with stable names, timestamps and identifiers — the same raw material behind every dashboard you already run.

    Four Layers Worth Instrumenting

    • Session: one human sitting down with one agent. Start, end, resume, and the compaction events that mark the moment the conversation outgrew its window. Session-level data tells you about interruptions and rework.
    • Workflow and stage: the unit of intent. A stage has a name, a lead, inputs and outputs, and it either completes, is revised or is skipped. This is where the equivalent of a "request" lives, and where most of your SLIs will come from.
    • Tool call: every file read, edit, shell command and sub-agent dispatch. High cardinality, high volume, and the only place you will ever see the difference between a model that is thinking and a model that is thrashing.
    • Artifact and cost: what was actually produced, which files changed, how many tokens it took and what that cost. Without this layer you cannot answer the only question your finance team will ask.

    AI-DLC Already Emits the Events

    If you want a worked example of a harness that treats its own execution as an observable system, look at AI-DLC, the AWS Labs implementation of the AI-Driven Development Life Cycle. It runs a harness-neutral core across Claude Code, Kiro, Codex CLI, Cursor, opencode and GitHub Copilot, structuring work into 5 phases and 33 stages with human approval gates between them.

    The part an SRE should care about is the audit trail. Every intent carries an append-only event log written as per-clone shards, and the engine emits 99 typed event types into it. A sample of the vocabulary:

    WORKFLOW_STARTED     PHASE_VERIFIED       STAGE_STARTED
STAGE_REVISING       STAGE_COMPLETED      STAGE_SKIPPED
GATE_APPROVED        GATE_REJECTED        HUMAN_TURN
SENSOR_FIRED         SENSOR_PASSED        SENSOR_FAILED
BOLT_STARTED         BOLT_COMPLETED       BOLT_FAILED
SWARM_STARTED        SWARM_UNIT_CONVERGED SWARM_UNIT_FAILED
RULE_LEARNED         ERROR_LOGGED         RECOVERY_COMPLETED

    That is not a log file. That is a schema. Names are stable, transitions are paired, failures have their own types rather than being buried in free text, and every row carries an ISO timestamp. It is close enough to a span stream that turning it into one is mostly mechanical: the workflow becomes a trace, each phase and stage becomes a span, gate and sensor events become span events, and the identifiers you need for correlation — intent, space, unit, repository — are already on the rows.

    Golden Signals for an Agent Harness

    The four golden signals translate more cleanly than you might expect:

    • Latency: wall-clock duration of a stage, and separately the time a stage spends waiting on a human at an approval gate. Keep those two apart or your percentiles will measure your team's calendar, not your harness.
    • Traffic: stages executed, units generated, workflows started per day. This is your denominator and you will want it before you want anything else.
    • Errors: BOLT_FAILED, SENSOR_FAILED, SWARM_UNIT_FAILED, ERROR_LOGGED, and the quieter signal of GATE_REJECTED — a human looked at the output and sent it back.
    • Saturation: context-window headroom before compaction, concurrent sub-agent slots in use, and provider rate-limit pressure. Saturation in an agent harness looks like a session that suddenly forgets what it was doing.

    Wire It Into the Stack You Already Have

    Resist the urge to buy a separate "AI observability" product on day one. Emit OpenTelemetry spans from the harness hooks, tag them with the workflow identifiers, and send them to the same backend that holds your service traces. The payoff is correlation: when a change ships and an SLO starts burning, you want the trace of the agent run that produced it sitting one click away, the same way exemplars link a metric spike to the span that caused it. Emit the event payloads as structured logs rather than prose, and keep the field names identical to the audit event types so nobody has to maintain a translation table.

    Start With One Question

    You do not need all four layers in the first week. Pick the question that is costing you the most right now — usually "how often does a run need human rework before it is accepted?" — and instrument only what answers it. That single ratio is the first SLI of your delivery factory, and once you have it, the rest of the instrumentation tends to justify itself.
