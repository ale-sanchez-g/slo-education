    Rules, Sensors and Gates: The SRE Control Loop Inside the AI-DLC

    Rules feed forward, sensors feed back and gates hold the line. Learn how the AI-DLC control loop maps onto SRE practice and why deterministic checks beat model self-assessment.

    Asking the Model If It Did a Good Job

    There is a failure mode that every team building on agents discovers within about a fortnight. You ask the agent to check its own work, it reports that everything looks correct, and it is wrong. Not maliciously — it simply has no independent access to ground truth. Self-assessment inherits every error in the work it is assessing.

    SRE has never trusted a component's opinion of its own health either. We do not ask a service whether it is up; we measure it from outside, with a probe that does not share its fate. The same instinct is what makes an AI delivery pipeline trustworthy, and the most interesting thing about the AI-DLC implementation is that it builds that instinct into the engine rather than leaving it to prompt discipline.

    A Control Loop, Named as Such

    AI-DLC's documentation describes two mechanisms as the two halves of a control loop, which is not language you often see in a developer tool.

    Rules are the feedforward half. A rule is a persistent behavioural instruction — your company's logging standard, your naming conventions, the library you have standardised on — authored once and pulled into context for every stage it covers. Rules resolve through a strict-additive chain of five layers: organisation, team, project, phase, stage. Broader layers are never overridden, only added to, so a team cannot quietly opt out of an org-level security rule by writing a narrower one.

    Sensors are the feedback half. A sensor is a deterministic verification check defined by a manifest — a linter, a type check, a custom validator. Sensors fire on matching write and edit calls, or once per deliverable at the approval gate, and they record SENSOR_FIRED, SENSOR_PASSED and SENSOR_FAILED events. Bindings can be advisory or blocking, and blocking findings require either a correction or an explicit, audited override.

    Read that as an SRE and the mapping is immediate. Rules are your golden path and your platform defaults: the things you set up so the common case is correct by construction. Sensors are your monitoring and your assertions: the things that tell you the truth when the common case did not hold. A pipeline with only rules is a system with no monitoring. A pipeline with only sensors is a system with no platform engineering — you catch everything late and fix it by hand.

    A Loss Function Needs a Signal

    The AI-DLC method definition paper describes human validation points as functioning "like a loss function" — catching and correcting errors early, before they snowball downstream. It is a good metaphor and it repays being taken literally, because a loss function has a requirement the metaphor quietly hides: it needs a measured error to act on. Gradient descent without a loss value is just descent.

    A human reviewing output at an approval gate is computing that error term from whatever they can see in the time they have. At sprint cadence, that works. At the hours-or-days cadence the paper is designing for — where a Bolt is the smallest iteration and Units are deliberately decoupled so they can run in parallel — human attention becomes the scarcest input in the system, and spending it on things a program could have checked is the most expensive mistake available.

    That is what sensors are for. They compute the cheap, mechanical part of the error term so the human can spend their pass on the part that genuinely needs judgement: is this the right thing to build, does this trade-off hold, is this risk one we accept. Which reframes the usual design question. It is not "how many gates should we have", it is "at each gate, which part of the error term is the machine computing, and which part is the human?" A gate where a senior engineer is checking formatting is a gate that is wasting a loss function.

    Advisory, Blocking, and the Audited Override

    The advisory-versus-blocking distinction deserves more attention than it usually gets, because it is the same decision as page-versus-ticket in alerting, and it goes wrong in the same way.

    Make everything blocking and the agent grinds to a halt on style opinions while the humans learn to override reflexively — which is exactly how alert fatigue works, and it destroys the signal in precisely the same manner. Make everything advisory and nothing is actually enforced; findings scroll past in a transcript nobody reads.

    The rule of thumb that survives contact with reality: blocking sensors check things that are objectively wrong and cheaply verifiable — the code does not compile, the types do not check, a secret is in the diff, a required migration is missing. Everything about taste, structure or preference starts advisory and gets promoted only when you have evidence from the audit trail that it is being ignored and causing rework.

    There is precedent in the method for keeping the human-judgement checks explicit rather than implicit. Among the artefacts the paper deliberately retains from older methods is the Risk Register, on the grounds that it "ensures AI-generated plans and codes comply with organizational risk frameworks" — kept, but optimised for real-time use so it does not slow the iteration down. That is the right instinct applied to the whole control loop: the question is never whether to keep a check, it is whether the check runs at the speed of the process it governs.

    The audited override matters as much as the block. A blocking check with no escape hatch gets disabled the first time it is wrong at 2am. A blocking check with an override that leaves a row in the audit trail gets used correctly, because the escape is available and visible. This is the same design as an error budget policy exception: you can always ship anyway, and the decision is on the record with a name attached.

    Gates Are Not Ceremony, They Are Consistency Checks

    AI-DLC puts a human approval gate after each stage, and an automated verification gate at each phase boundary. The verification gate is the one an SRE should find familiar: it checks that every required artefact from the completing phase exists, that traceability links are intact — every requirement maps to a story — and that there are no orphaned artefacts or dangling references before downstream stages build on them.

    That is a referential integrity check, run at the boundary where corruption becomes expensive. It is the same reason we validate config before rollout instead of discovering the typo through a 500 rate. Long agent runs are especially prone to quiet drift: a requirement gets dropped three stages back, everything downstream still looks plausible, and nothing surfaces until a human reads the final diff closely. Boundary verification is what turns that from a discovery into a detection.

    The Learning Loop Is a Blameless Retro

    The third piece closes the loop. During a stage, corrections get recorded as observations; at the approval gate, they are surfaced, the human confirms which to keep, and each confirmed learning is written as a durable practice — or scaffolds a new sensor — so it applies to the next workflow. The events are RULE_LEARNED and SENSOR_PROPOSED.

    This is a blameless post-incident review compressed into a single run. A correction is an incident, however small. The valuable output is not the fix — the fix already happened — but the change to the system that stops the class of problem recurring. A team that files corrections only as chat messages is a team relearning the same lesson every sprint. Promoting a correction into a rule, and a repeated correction into a sensor, is the agent-era version of "turn the action item into a test".

    The instinct to check: when a correction becomes a rule, does it also deserve a sensor? Rules shape behaviour probabilistically. Sensors verify deterministically. Anything you would be genuinely upset to ship needs both.

    Version the Loop, Review the Loop

    Rules and sensor manifests are files. Treat them the way you would treat SLO definitions in version control: in the repository, changed by pull request, reviewed by someone other than the author. A rule change alters the behaviour of every future run in its scope, which makes it a higher-blast-radius edit than most application code — and it is exactly the kind of change that tends to be made in a hurry, at the end of a frustrating session, by whoever was closest to the keyboard.
