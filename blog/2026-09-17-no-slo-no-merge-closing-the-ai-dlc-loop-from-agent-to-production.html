    No SLO, No Merge: Closing the AI-DLC Loop from Agent to Production

    AI-DLC puts observability, incident response and SLO reporting inside the lifecycle. Learn how to make agents ship dashboards, alerts and error budgets alongside the code.

    The Code Shipped. Who Owns It at 3am?

    An AI factory that ends at "the tests pass" has not finished the job; it has moved the unfinished part somewhere less convenient. Somebody still has to answer a page about the service the agent built, and that somebody will be a human with no memory of writing it, reading code they have never seen, at an hour when nobody reads carefully.

    This is the failure that will define the next couple of years of AI-assisted delivery. Generation capacity has raced ahead; operational readiness has not moved. The teams that get through it will be the ones who treat observability as a deliverable of the build, not a follow-up ticket that never reaches the top of a backlog.

    Operations Belongs Inside the Lifecycle

    The structural answer is to make operations a phase, not an afterthought. AI-DLC does this explicitly: its fifth phase, Operation, is seven stages of production work owned by an operations agent.

    • 4.1 Deployment Pipeline — CD configuration, deployment strategy and a rollback runbook
    • 4.2 Environment Provisioning — environment inventory and validation report
    • 4.3 Deployment Execution — deployment log, smoke tests, health checks
    • 4.4 Observability Setup — dashboards, alarms, SLO config
    • 4.5 Incident Response — runbooks, incident plan, escalation matrix
    • 4.6 Performance Validation — load test results, NFR validation matrix
    • 4.7 Feedback & Optimization — SLO report, cost analysis, feedback loop document

    Note what stage 4.4 lists as an artefact: SLO config, sitting beside the dashboards and alarms as a thing the run is expected to produce. And the phase is not only at the end. During Construction, stage 3.2 gathers non-functional requirements per unit of work — performance, security, scalability, reliability and observability NFRs — so the instrumentation requirement is captured while the design is still being made, not retrofitted after the code exists.

    There is a catch worth naming. Every Operation stage is conditional, and the whole phase is skipped for the MVP and proof-of-concept profiles. That is a defensible default — a PoC genuinely does not need an escalation matrix — but it is also exactly how unobserved services reach production. A PoC that survives contact with real users is promoted by a decision someone makes in a hurry, and nothing in the tooling will stop them. The organisational rule has to do that work: a profile that skips Operation may not serve production traffic until it has been re-run through one that does not.

    Make "No SLO, No Merge" a Real Gate

    Requiring observability as an artefact only means something if something checks. The practical version is a deterministic check in the same family as AI-DLC's sensors, or simply a required CI job, that fails a change when the unit it belongs to has no reliability definition attached:

    Definition of Done for a unit of work
  [ ] The user journey this unit serves is named
  [ ] At least one SLI is defined as a ratio of good to valid events
  [ ] The SLI is emitted by the code in this change, not inferred later
  [ ] An SLO target and rolling window are committed to the repository
  [ ] A burn rate alert routes to a named owner
  [ ] A runbook exists for that alert and says what to do first

    Agents are, in fact, unusually good at producing these artefacts, because the cost of writing a runbook has always been the tedium rather than the difficulty. What they cannot supply is the judgement about what the target should be or who gets woken up. Keep those two decisions at the approval gate and let the machine do the rest.

    The SLI line is the one that matters most. An SLO written against a metric the service does not emit is a wish, and it will read as 100% forever. Require that the instrumentation ships in the same change as the objective, and store both in the repository as SLOs as code so a reviewer sees the target and the query together. The error budget calculator is the fastest way to sanity-check what a proposed number actually costs in minutes per month.

    Incident Response When the Author Is an Agent

    Traditional incident response leans hard on a piece of context that is quietly disappearing: somewhere in the building is a person who remembers why the code is like that. When the author was an agent, that person does not exist, and the substitute has to be written down.

    Two things change in practice. First, provenance becomes an operational signal. If your audit trail records which intent, which unit and which run produced a change, then an incident investigation can start from the failing deployment and walk back to the requirements, the design decisions and the approval gates behind it. That is a better trail than most human-authored code leaves, provided you kept it.

    Second, the incident response escalation matrix needs an honest row for AI-generated components: who is the accountable human owner, and what is the fallback when the code is not understood well enough to fix safely under time pressure? Usually the fallback is the rollback runbook from stage 4.1, which is a strong argument for making sure that artefact is real rather than a heading in a document.

    And then run the post-incident review as you always would, blamelessly, with one addition. Ask whether the lifecycle should have caught it: was there a missing NFR at 3.2, a sensor that should have been blocking, a rule that would have prevented the pattern? In an AI factory, the highest-leverage action item is rarely the code fix. It is the change to the loop that prevents the whole class.

    Close the Loop

    The last stage, 4.7, produces an SLO report and a cost analysis, and its output feeds back to the start of the lifecycle as the input to the next intent. That arrow is the whole argument in one line: production reliability data is not the end of the pipeline, it is the beginning of the next one.

    A factory that runs in the dark and never reads its own instruments will drift until something expensive happens. One that feeds SLO reports and error budget burn back into what it builds next is doing the thing SRE has always been for — using evidence about how the system behaves in the real world to decide what to change. That the builder is now a machine does not change the discipline. It just raises the cost of not having it.
